책이지 MCP 설계도

「책이지」 앱이 완성되었다고 가정하고, 그 자동화 전체가 MCP 위에서 어떻게 돌아가며 어떻게 전국으로 번지는지를 끝까지 따라가는 문서. 이용자의 말 한마디부터 다른 도시의 도입 체크리스트까지 — 챗봇은 답을 주고 실행은 이용자가 하지만, 이 설계의 에이전트는 판정하고 신청까지 대신 한다.

먼저 한 문장. MCP 서버는 기계가 아니라 약속입니다. "도서관에 시킬 수 있는 일은 이 열 가지이고, 각각은 이런 모양의 요청을 받아 이런 모양의 답을 돌려준다"라는 약속을 코드로 굳혀 놓은 것. 에이전트(AI)는 이 약속만 알면 되고, 그 약속 뒤에서 실제로 어느 시스템이 움직이는지는 몰라도 됩니다. 콘센트 비유가 정확히 여기에 걸립니다 — 벽 뒤의 발전소가 화력이든 태양광이든, 플러그 규격만 맞으면 드라이어는 돌아갑니다. 이 문서는 그 "벽 뒤"를 전부 열어 보입니다.

01김순자 씨의 3분 — 완성된 책이지의 실제 동작

김순자 씨(75)는 상동도서관 근처에 삽니다. 스마트폰에 책이지가 깔려 있고, 지난달 시 통합회원 아이디로 한 번 로그인해 둔 상태입니다. 손녀가 말한 책이 생각나 마이크를 누릅니다.

김순자"그 왜… 나미야 잡화점인가 하는 책 좀 빌려줘요."

책이지"『나미야 잡화점의 기적』(히가시노 게이고)으로 찾았어요. 상동도서관 책은 지금 대출 중인데, 한울빛도서관 책을 상동으로 가져다 드릴 수 있어요. 무료이고 2~3일 걸려요. 신청할까요?"

김순자"응, 해줘요."

책이지"접수했어요. 도착하면 전화로 알려드릴게요. 도착 후 3일 안에 찾아가시면 되고, 책이 떠나기 전이면 취소도 돼요."

겉에서 보면 대화 네 마디. 속에서는 도구 호출 다섯 번이 오갔습니다. 아래가 그 순서도입니다.

겉으로는 여기서 끝이지만, 접수 뒤에도 도구 두 개가 더 움직입니다. track_request는 "내 책 어디까지 왔어요?"에 답하고(접수 → 자료 확보 → 이송 → 도착·수령 대기 → 대출 완료), cancel_request는 이송이 시작되기 전이라면 이용자 본인 취소를 받아 한도를 즉시 되돌려 놓습니다. 서가에 책이 실제로 없거나 이송 전에 남이 먼저 빌려 가면 신청은 접수 뒤에 실패할 수 있고, 그때도 한도는 복원됩니다. 이 "신청 이후"까지 도구 계약에 넣은 것이 v0.3의 요지입니다.

핵심은 에이전트가 도서관에 대해 아는 것이 전혀 없다는 점입니다. 알파스가 뭔지, 정보나루 지역코드가 31050인지, 상호대차 한도가 몇 권인지 모릅니다. 에이전트가 아는 것은 열 개의 도구 이름과 그 사용법뿐이고, 나머지는 전부 도구 뒤의 커넥터가 처리합니다. 그 열 개가 아래 명세입니다.

①과 ④가 실제로 오간 전문(電文)은 이렇게 생겼습니다. 이게 MCP의 실체입니다 — 그냥 모양이 정해진 질문과 답변입니다.

① search_item — 발화를 책으로 확정
→ 요청  { "tool": "search_item",
          "arguments": { "utterance": "그 왜 나미야 잡화점인가 하는 책", "lang": "ko" } }

← 응답  { "isbn13": "9788972756194",
          "title": "나미야 잡화점의 기적", "author": "히가시노 게이고",
          "publisher": "현대문학", "confidence": 0.97,
          "evidence": "정보나루 srchBooks · exactMatch" }   // 근거가 항상 따라온다

→ 요청  { "tool": "request_service",
          "arguments": { "user": "tok_8f3a…",          // 회원번호가 아니라 임시 토큰
                         "isbn13": "9788972756194",
                         "from": "한울빛", "pickup": "상동",

                         "client_request_id": "c-7d21…" } }  // false면 거부 · 같은 id가 다시 오면 새 신청 대신 기존 접수번호

← 응답  { "receipt": "ILL-2027-0412-0037", "eta_days": "2~3",
          "executed_via": "알파스 커넥터 v1" }

02전체 해부도 — 다섯 층, 그리고 콘센트

완성형 책이지는 다섯 층으로 쌓입니다. 가운데 층이 MCP 도구 서버 — 멀티탭처럼 열 개의 "콘센트"가 두 줄로 뚫려 있고, 위에서는 에이전트가 플러그를 꽂고, 아래에서는 커넥터들이 전기를 공급합니다.

층실체물리적으로 어디에누가 만드나
L1 입구앱(PWA)·전화·창구 화면이용자 손 안 / 도서관 데스크부천 (시제품 확장)
L2 에이전트LLM 호출 + 대화 관리 프로그램공공기관용 클라우드 1대부천 (본사업)
L3 MCP 서버도구 10종을 정의한 프로그램 하나같은 클라우드, 같은 서버 가능부천이 만들고 → 전국이 공유
L4 커넥터시스템별 번역 모듈정보나루용은 클라우드 / 알파스용은 도서관 내부망 접점부천 → 같은 시스템 쓰는 곳은 재사용
L5 실물정보나루·알파스·SSO·통신사이미 있는 곳아무도 (이미 존재)
"MCP 서버"라는 말에서 서버실의 기계를 떠올릴 필요가 없습니다. L2~L4는 전부 합쳐 클라우드 가상서버 한 대에 올라가는 프로그램들이고, MCP 서버는 그중 한 프로그램의 이름일 뿐입니다.

03표준 도구 10종 명세 — 약속의 전문

열 도구는 일부러 도서관 용어가 아닌 중립어로 지었습니다. request_service가 "상호대차 신청"이 아니라 "서비스 신청"인 이유 — 같은 콘센트에 나중에 공연 예매를 꽂기 위해서입니다(7장). ①·④의 전문은 1장에서 봤으니, 표로 열을 한눈에 정리합니다.

도구받는 것돌려주는 것부천에서의 실제 동작상태
search_item일상어 발화, 언어ISBN·서지·확신도·근거정보나루 srchBooks (exactMatch + 판본 보정)구현
check_availabilityISBN, 범위, 실시간 여부기관별 상태 목록 + 다음 갈래(방문·관내 신청·예약·책바다 안내)알파스 실시간 → 실패 시 정보나루(전일) 폴백. 관내 소장은 있으나 전부 대출 중이면 전국이 아니라 예약으로구현*
check_policy이용자 토큰, ISBN, 수령관가능 여부 + 규정별 판정 근거7개 규정을 설정 파일 기준으로 검사 (4장)구현
request_service판정 통과 신청서 + 이용자 확인 + 요청 고유번호접수번호, 예상 소요알파스에 상호대차 트랜잭션 생성 · 실행 직전 재판정 · 같은 고유번호가 다시 오면 기존 접수번호 반환(재시도 중복 방지)규격 검증*
track_request이용자 토큰, 접수번호현재 상태·이력접수 → 자료 확보 → 이송 → 도착·수령 대기 → 대출 완료 (예외: 실패·취소) — 실패 시 한도 즉시 복원구현(모의 상태 전이)
cancel_request이용자 토큰, 접수번호취소 결과, 복원된 한도이송 시작 전(접수 상태)에만 이용자 본인 취소 · 그 뒤엔 도서관 문의로 안내구현
find_alternativeISBN, 이용자 조건대체자료 존재·유형국가서지 대체자료목록 조회 (점자·오디오북) → 책나래 분기규격 검증*
notify_user사건(도착 등), 선호 채널발송 결과문자 또는 TTS 음성전화 — 김순자 씨는 전화규격 검증*
suggest_items이용자, 권수이달의 추천 목록[자동화 확장] AI 책큐·정보나루 추천 연계구현*
manage_mandate이용자, 동작(생성·조회·해지)구독 위임장[자동화 확장] 책이지 패스의 동의 장치 — 위임 실행·범위 밖 건너뜀·즉시 해지구현

표의 "상태" 열이 현재 위치입니다. 2026. 9. 기준, 핵심 8종과 자동화 확장 2종(구독형 「책이지 패스」용) 열 도구 전부가 실제 MCP 전송(stdio JSON-RPC) 위의 참조 서버(v0.3)로 구현되어 적합성 시험 33건을 통과했습니다. 시험이 고정해 둔 것은 김순자 시나리오 전 단계, 무확인 실행 거부, 실행 후 한도 갱신, 전국 폴백과 전일 기준 명시, 규정 설정 파일 교체만으로 판정이 달라지는 것, 사전 위임의 자동 실행과 범위 밖 건너뜀과 해지 즉시 거부, 그리고 신청 이후의 생애주기 — 상태 추적, 실패·취소 시 한도 복원, 같은 요청이 재전송되어도 접수는 한 건 — 입니다. 확장 2종이 더하는 것은 동의 방식의 진화입니다 — 건별 확인이 「범위 명시 사전 위임 + 사후 통지 + 즉시 해지」로 바뀝니다. 별표(*)는 도서관리시스템 쪽이 모의 커넥터라는 뜻입니다. 모의 커넥터의 함수 일곱 개 (회원 현황·실시간 재고·서가 비치 여부·신청 생성·알림 발송·신청 상태 조회·신청 취소) 목록이 곧 본사업에서 벤더에게 제시할 연동 요구서이며, 실측 소장 데이터(2026. 8. 18. 64건)와 가상 회원 위에서 동작합니다. 실행 계층을 진짜 알파스에 붙이는 일이 본사업의 몫입니다.

2026. 9. 운영 규정 조사로 고친 것. 지자체 통합도서관 다섯 곳(강남·청주·부산·용인·광진)의 공개 상호대차 규정을 대조한 결과, 책바다는 관내 미소장 자료가 대상이라 "관내 소장은 있으나 전부 대출 중"은 전국이 아니라 예약으로 가야 하고, 책바다는 별도 가입·사서 승인·실비 결제를 거치는 별도 시스템이라 에이전트가 대신 신청할 수 없습니다. 그래서 3단계는 「대행」이 아니라 「안내와 승인 요청 전달」이고, 대행의 범위는 관내 상호대차입니다. 도착 후 보관기한(통상 3일) 안에 찾아가지 않으면 열흘에서 한 달의 신청 제한이 따르는 미수령 제재, 이용자 취소는 접수 상태에서만 된다는 점도 설계에 들어갔습니다. 이 항목들의 설정값(4장 YAML의 v0.4 예정 줄)은 다음 판의 규정 8종에 반영됩니다.

04커넥터의 실체 — 번역기 한 편의 속살

커넥터가 실제로 어떤 물건인지, 알파스 커넥터의 check_policy 부분을 의사코드로 보입니다. 읽는 데 프로그래밍 지식이 필요하지 않게 썼습니다 — 줄마다 무슨 일이 벌어지는지가 오른쪽 주석에 있습니다.

alpas_connector / policy.py — 규정 판정의 실제 구현 (의사코드)
RULES = load("config/bucheon.yaml")          # 규정 숫자는 코드가 아니라 설정 파일에 (아래)

def check_policy(user_token, isbn13, pickup):
    member = alpas.member_status(              # 알파스에 회원 현황을 묻는다
        vault.resolve(user_token))             # 진짜 회원번호는 금고 안에서만 풀린다 (5장)

    checks = [
      rule("수령관 동일도서 비치 시 불가",
           not alpas.on_shelf(pickup, isbn13)),          # 상동 서가에 지금 꽂혀 있나?
      rule(f"상호대차 {RULES.ill_limit}권",
           member.ill_count < RULES.ill_limit),            # 김순자 씨는 지금 2권 → 통과
      rule(f"통합 {RULES.total_limit}권",
           member.total_loans < RULES.total_limit),
      rule(f"도서관별 {RULES.per_lib_limit}권",
           member.loans_at(pickup) < RULES.per_lib_limit),
      rule("연체·정지 회원 불가",
           not member.suspended and member.overdue == 0),   # 부천 고시 4종 + 도서관계 일반 3종 = 7종
      rule("상호대차 제외 자료 아님",
           material(isbn13).kind not in RULES.excluded),  # 신착·참고자료 등 — 세부값은 기관이 확정
      rule("동일 도서 중복 신청 아님",
           not alpas.has_active_request(member, isbn13)),
    ]
    return Decision(allowed=all(checks), why=checks)   # 판정 + 근거를 함께 돌려준다

이 파일이 하는 일의 전부가 번역입니다. 왼쪽에서 표준 질문(check_policy)이 들어오면, 알파스가 알아듣는 말(회원 현황 조회, 서가 재고 조회)로 바꿔 묻고, 답을 다시 표준 모양으로 싸서 돌려줍니다. 정보나루 커넥터도, 나중에 만들 다른 시스템 커넥터도 구조가 같습니다.

규정은 코드가 아니라 설정이다

위 코드에 부천의 "5권·20권·5권"이 한 글자도 없다는 점을 봐 주세요. 숫자는 전부 설정 파일에 삽니다. 이 한 수가 6장의 확산을 가능하게 만듭니다. 부천이 고시한 4종 뒤에 붙은 3종(연체·정지, 제외 자료, 중복 신청)은 도서관계에서 일반적인 조건이라 설정 파일에 예시값으로만 두고 도입 기관이 확정합니다.

config/bucheon.yaml — 부천의 모든 지역 고유값
region_code: 31050                # 정보나루 세부지역 코드
libraries: { 상동: 141321, 꿈빛: 141065, … 16개관 }
rules:
  ill_limit: 5                   # 상호대차 1인 한도
  total_limit: 20                # 시 통합 대출 한도
  per_lib_limit: 5               # 도서관별 한도 (직접+상호대차 합산)
  block_if_pickup_on_shelf: true # 수령관 비치 시 신청 불가 규정
  excluded: [신착도서, 참고자료]   # 상호대차 제외 자료 (예시값 · 기관 확정)
  block_suspended: true         # 연체·정지 회원 불가
  block_duplicate: true         # 동일 도서 중복 신청 불가
  hold_days: 3                  # v0.4 예정 — 도착 후 보관기한
  no_show_penalty_days: 14      # v0.4 예정 — 미수령 제재 (기관 확정: 10~30일)
  cancel_allowed_states: [접수]   # v0.4 예정 — 이용자 취소 가능 상태
sso: sso.bucheon.go.kr
notify_channels: [sms, voice_call]
전일 기준 문제는 여기서 끝납니다. 관내 16개관의 재고·대출은 알파스 커넥터가 실시간으로 답하므로, 정보나루의 D-1 데이터는 "다른 지역에 있나"를 보는 광역 조회와 비상시 폴백으로만 쓰입니다. 시제품의 한계였던 것이 완성형에서는 역할 분담이 됩니다.

05어디서 돌고, 무엇이 지켜지나

물리적 배치는 단출합니다. 공공기관용 클라우드의 가상서버에 에이전트·MCP 서버·정보나루 커넥터·알림 커넥터가 올라가고, 알파스 커넥터만 도서관 정보시스템과 만나는 접점(내부망 연계 구간)을 가집니다. LLM은 API로 호출하며, 계약에 따라 국내 리전·공공 전용 모델로 둘 수 있습니다. 모델 교체가 생겨도 L3 아래는 아무것도 바뀌지 않습니다 — 이것도 MCP 분리의 효과입니다.

개인정보는 어디까지 가는가

가장 예민한 질문이라 표로 못박습니다. 원칙은 하나 — 언어모델은 판단에 필요한 최소한만 보고, 신원은 금고(vault) 밖으로 나가지 않는다.

편의성의 값을 이용자가 치르지 않게 — 아홉 원칙

말 한마디로 신청이 끝나는 편의성에는 그만큼의 위험이 따릅니다. 목소리만으로 본인을 확인할 수 있는가, 발화에 섞인 명령어는 어떻게 되는가, 남의 명의로 한도를 소진하는 장난은 막히는가. 답은 아홉 원칙이고, 그중 다섯은 이미 참조 서버와 시연 웹에 구현되어 있습니다.

원칙내용상태
AI는 안내만, 실행은 규정 엔진이언어모델은 신청을 직접 실행하지 못한다. 규정을 통과한 요청만 도구 계층이 실행한다구현
AI는 회원 식별자를 모른다언어모델에는 토큰만 전달되고, 회원번호와의 대응표는 금고 한 곳에만 둔다구현
발화는 입구에서만발화는 ISBN으로 정규화된 뒤 안쪽으로 들어가므로 문장이 명령이 될 수 없다구현
목소리는 서버에 남지 않는다기기 내장 음성 인식만 쓰고 녹음을 전송하지 않는다구현
규정 한도가 곧 안전장치1인 5권 한도가 대량 신청을 구조적으로 막는다구현
취소할 수 있는 일만 대신한다상호대차 신청은 취소 가능하다. 결제·회원정보 변경은 에이전트의 범위 밖이다설계
위험한 일일수록 문을 세게 잠근다행위의 위험도에 따라 인증 강도를 달리한다 (아래 표)설계
모르는 실행은 없다모든 대행 실행은 통지·즉시 취소·기록을 동반한다일부 구현
필요한 숫자 두 개만 본다대출 이력이 아니라 현재 권수와 연체 여부만 조회한다설계

인증은 새로 만들지 않고 기존 회원 인증 위에 「등록된 기기」를 얹습니다. 비밀번호 대신 기기의 생체인증으로 본인을 확인하는 패스키(passkey) 방식은 서버에 비밀번호가 남지 않아 유출될 것이 없고, 기기에 묶여 공용 PC에서는 동작하지 않습니다. 등록된 기기라도 자동으로 열리는 것은 조회와 무료 신청까지이며, 실비가 드는 신청과 위임 생성은 생체인증을 한 번 더 거칩니다. 전화는 등록된 번호 발신 확인 위에서 저위험 행위만 다룹니다.

해지만 전화로 열어 둔 이유 — 안전 쪽으로 가는 문은 항상 가장 쉽게. 사고가 나더라도 피해는 「책 한 권이 잘못 신청됨」에 그치고, 그마저 통지와 취소로 되돌릴 수 있게 하는 것이 이 원칙들의 목적입니다. 그리고 사실(소장·규정)은 전부 도구가 답하므로 LLM이 지어낼 자리가 구조적으로 없습니다 — LLM의 일은 해석과 문장뿐입니다.

전화 한 통 모드 — 화면이 없어도 같은 절차

L1의 세 입구 가운데 전화는 스마트폰도 홈페이지도 다루기 어려운 분을 위한 문입니다. 대표번호로 걸면 같은 에이전트가 목소리만으로 안내하고, 등록된 번호로 걸었는지 확인한 뒤 관내 상호대차 신청까지 마칩니다. 시연 웹의 📞 단추에서 그 통화 흐름 (인사 → 책 말하기 → 등록 번호 확인 → 판정 낭독 → 예/아니오 → 접수 → 「책이지가 대신 한 일」)을 열 개 언어로 그대로 체험할 수 있습니다. 다만 이것은 대화 흐름의 검증이지 전화망 연결이 아닙니다 — 실제 회선은 통신 사업자 연동(AI 콜센터 API 또는 070 회선과 음성 서버)이 필요한 본사업의 몫이며, 그때도 L2 아래는 아무것도 바뀌지 않습니다. 입구가 하나 늘어도 절차는 하나입니다.

06다른 도시가 가져가는 날 — 확산의 실제 절차

이제 핵심 질문. 가령 알파스를 쓰는 A시 도서관이 책이지를 도입하기로 했다면, A시가 실제로 해야 하는 일은 무엇인가? 답: 설정 파일 하나를 쓰고, 이미 있는 부품을 내려받아 조립하는 것입니다. 코딩이 등장하는 순간은 단 한 경우뿐입니다.

#A시가 하는 일성격규모
1도서관 코드표 교체 — 자기 분관들의 정보나루 코드설정반나절
2규정 YAML 작성 — 자기 시의 한도·규칙 숫자설정반나절
3자기 시 SSO 연동 정보 입력설정+협의시 정보부서 협의
4도서관리시스템 커넥터 연결 — 알파스면 부천 것 재사용재사용0 (이미 있음)
5다른 시스템이라면 → 그 시스템용 커넥터 1회 개발개발 (유일)시스템당 1회, 전국이 공유
6적합성 시험 킷(33건) 통과 확인 — 통과가 곧 호환 보증검증자동, 수 분

1~2번이 어떤 일인지는 설정 파일을 나란히 놓으면 바로 보입니다. 왼쪽이 부천, 오른쪽이 가상의 A시 — 다른 것은 숫자와 코드뿐, 시스템은 한 글자도 다시 만들지 않습니다.

bucheon.yaml → a-city.yaml — 도입이란 곧 이 차이를 쓰는 일

08자주 나오는 질문

Q. MCP 서버를 도입하려면 서버(기계)를 새로 사야 하나?
아니요. "서버"라는 말에는 두 가지 뜻이 있습니다 — 서버실의 기계, 그리고 요청을 받아 답을 돌려주는 프로그램(식당의 "서버"가 종업원이듯, 역할 이름입니다). MCP 서버는 후자입니다. 실제로 이 프로젝트의 참조 서버는 파이썬 파일 하나(server.py)이며, 명령어 한 줄로 켜지고 꺼집니다. 컴퓨터 한 대에는 이런 서버 프로그램 여러 개가 동시에 올라갑니다. 예산서에 잡히는 것은 "서버 구입비"가 아니라 시 정보자원 또는 공공 클라우드의 이용료입니다.
Q. 알파스(벤더)가 연동에 협조하지 않으면?
조회까지는 정보나루만으로 시작할 수 있으므로 서비스 개시 자체는 막히지 않습니다. 실행(신청)만 벤더 API가 필요한데, 커넥터 하나로 자사 시스템을 쓰는 전국 도서관이 잠재 고객이 되는 구조라 벤더에게도 사업 기회입니다. 협의가 길어지면 과도기엔 화면 자동화로 대체하는 우회로도 있습니다(권장하지는 않음).
Q. AI가 개인정보를 학습하거나 유출하지 않나?
5장의 표가 답입니다. 이름·회원번호·연락처·이력 원본은 LLM에 아예 전달되지 않고, 임시 토큰과 요약 판정만 오갑니다. 호출 로그가 남아 감사도 가능합니다.
Q. AI가 잘못 알아들으면?
해석 결과는 항상 화면에 근거(서지·ISBN)와 함께 표시되어 이용자가 정정할 수 있고, 실행은 확인 한 번을 거쳐야만 일어납니다. 그리고 소장·규정 같은 사실은 LLM이 아니라 도구가 답하므로, 잘못 알아들어도 "없는 사실"이 만들어지지는 않습니다.
Q. 사고가 나면 — AI가 엉뚱한 책을 신청해 버리면?
최악의 경우가 「책 한 권이 잘못 신청됨」이 되도록 설계했습니다. 실행 전 확인 한 번, 실행 후 통지, 이송 전 즉시 취소(cancel_request)와 한도 복원, 그리고 모든 호출의 기록. 결제·회원정보 변경처럼 되돌리기 어려운 일은 처음부터 에이전트의 범위 밖입니다(5장 아홉 원칙).
Q. 전화로도 되나?
설계상 세 입구(앱·전화·창구) 중 하나이고, 시연 웹의 📞 단추에서 통화 흐름을 그대로 체험할 수 있습니다. 실제 전화망 연결은 통신 사업자 연동이 필요한 본사업 과제입니다(5장). 전화는 등록된 번호 발신 확인 위에서 조회·무료 신청·예약·위임 해지만 다루고, 실비가 드는 책바다 신청은 앱(재인증)이나 창구로 안내합니다.
Q. 정보나루 데이터가 전일 기준이라던데?
완성형에서는 관내 실시간을 알파스 커넥터가 맡고, 정보나루는 광역 조회와 폴백만 담당합니다(4장). 시제품 단계의 한계가 완성형의 역할 분담으로 바뀝니다.
Q. 그냥 도서관마다 챗봇 하나씩 만들면 안 되나?
됩니다 — 1,630번 만든다면. 그리고 그 1,630개는 서로 아무것도 공유하지 못합니다. MCP 구조의 요점은 잘 만드는 것이 아니라 한 번 만든 것이 남의 출발점이 되게 하는 것입니다. 상호대차가 장서를 공유하는 제도이듯, 이 설계는 개발을 공유하는 제도입니다.
