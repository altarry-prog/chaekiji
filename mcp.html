책이지 MCP 설계도

「책이지」 앱이 완성되었다고 가정하고, 그 자동화 전체가 MCP 위에서 어떻게 돌아가며 어떻게 전국으로 번지는지를 끝까지 따라가는 문서. 이용자의 말 한마디부터 다른 도시의 도입 체크리스트까지.

먼저 한 문장. MCP 서버는 기계가 아니라 약속입니다. "도서관에 시킬 수 있는 일은 이 여섯 가지이고, 각각은 이런 모양의 요청을 받아 이런 모양의 답을 돌려준다"라는 약속을 코드로 굳혀 놓은 것. 에이전트(AI)는 이 약속만 알면 되고, 그 약속 뒤에서 실제로 어느 시스템이 움직이는지는 몰라도 됩니다. 콘센트 비유가 정확히 여기에 걸립니다 — 벽 뒤의 발전소가 화력이든 태양광이든, 플러그 규격만 맞으면 드라이어는 돌아갑니다. 이 문서는 그 "벽 뒤"를 전부 열어 보입니다.

01김순자 씨의 3분 — 완성된 책이지의 실제 동작

김순자 씨(75)는 상동도서관 근처에 삽니다. 스마트폰에 책이지가 깔려 있고, 지난달 시 통합회원 아이디로 한 번 로그인해 둔 상태입니다. 손녀가 말한 책이 생각나 마이크를 누릅니다.

김순자"그 왜… 나미야 잡화점인가 하는 책 좀 빌려줘요."

책이지"『나미야 잡화점의 기적』(히가시노 게이고)으로 찾았어요. 상동도서관 책은 지금 대출 중인데, 한울빛도서관 책을 상동으로 가져다 드릴 수 있어요. 무료이고 2~3일 걸려요. 신청할까요?"

김순자"응, 해줘요."

책이지"접수했어요. 도착하면 전화로 알려드릴게요."

겉에서 보면 대화 네 마디. 속에서는 도구 호출 다섯 번이 오갔습니다. 아래가 그 순서도입니다.

핵심은 에이전트가 도서관에 대해 아는 것이 전혀 없다는 점입니다. 알파스가 뭔지, 정보나루 지역코드가 31050인지, 상호대차 한도가 몇 권인지 모릅니다. 에이전트가 아는 것은 여섯 개의 도구 이름과 그 사용법뿐이고, 나머지는 전부 도구 뒤의 커넥터가 처리합니다. 그 여섯 개가 아래 명세입니다.

①과 ④가 실제로 오간 전문(電文)은 이렇게 생겼습니다. 이게 MCP의 실체입니다 — 그냥 모양이 정해진 질문과 답변입니다.

① search_item — 발화를 책으로 확정
→ 요청  { "tool": "search_item",
          "arguments": { "utterance": "그 왜 나미야 잡화점인가 하는 책", "lang": "ko" } }

← 응답  { "isbn13": "9788972756194",
          "title": "나미야 잡화점의 기적", "author": "히가시노 게이고",
          "publisher": "현대문학", "confidence": 0.97,
          "evidence": "정보나루 srchBooks · exactMatch" }   // 근거가 항상 따라온다
④ request_service — 확인받은 신청만 실행
→ 요청  { "tool": "request_service",
          "arguments": { "user": "tok_8f3a…",          // 회원번호가 아니라 임시 토큰
                         "isbn13": "9788972756194",
                         "from": "한울빛", "pickup": "상동",
                         "confirmed_by_user": true } }  // 이 값이 false면 커넥터가 거부

← 응답  { "receipt": "ILL-2027-0412-0037", "eta_days": "2~3",
          "executed_via": "알파스 커넥터 v1" }

02전체 해부도 — 다섯 층, 그리고 콘센트

완성형 책이지는 다섯 층으로 쌓입니다. 가운데 층이 MCP 도구 서버 — 멀티탭처럼 여섯 개의 "콘센트"가 나란히 뚫려 있고, 위에서는 에이전트가 플러그를 꽂고, 아래에서는 커넥터들이 전기를 공급합니다.

층실체물리적으로 어디에누가 만드나
L1 입구앱(PWA)·전화·창구 화면이용자 손 안 / 도서관 데스크부천 (시제품 확장)
L2 에이전트LLM 호출 + 대화 관리 프로그램공공기관용 클라우드 1대부천 (본사업)
L3 MCP 서버도구 6종을 정의한 프로그램 하나같은 클라우드, 같은 서버 가능부천이 만들고 → 전국이 공유
L4 커넥터시스템별 번역 모듈정보나루용은 클라우드 / 알파스용은 도서관 내부망 접점부천 → 같은 시스템 쓰는 곳은 재사용
L5 실물정보나루·알파스·SSO·통신사이미 있는 곳아무도 (이미 존재)
"MCP 서버"라는 말에서 서버실의 기계를 떠올릴 필요가 없습니다. L2~L4는 전부 합쳐 클라우드 가상서버 한 대에 올라가는 프로그램들이고, MCP 서버는 그중 한 프로그램의 이름일 뿐입니다.

03표준 도구 6종 명세 — 약속의 전문

여섯 도구는 일부러 도서관 용어가 아닌 중립어로 지었습니다. request_service가 "상호대차 신청"이 아니라 "서비스 신청"인 이유 — 같은 콘센트에 나중에 공연 예매를 꽂기 위해서입니다(7장). ①·④의 전문은 1장에서 봤으니, 표로 여섯을 한눈에 정리합니다.

도구받는 것돌려주는 것부천에서의 실제 동작상태
search_item일상어 발화, 언어ISBN·서지·확신도·근거정보나루 srchBooks (exactMatch + 판본 보정)구현
check_availabilityISBN, 범위, 실시간 여부기관별 상태 목록알파스 실시간 → 실패 시 정보나루(전일) 폴백구현*
check_policy이용자 토큰, ISBN, 수령관가능 여부 + 규정별 판정 근거4개 규정을 설정 파일 기준으로 검사 (4장)구현
request_service판정 통과 신청서 + 이용자 확인접수번호, 예상 소요알파스에 상호대차 트랜잭션 생성규격 검증*
find_alternativeISBN, 이용자 조건대체자료 존재·유형국가서지 대체자료목록 조회 (점자·오디오북) → 책나래 분기규격 검증*
notify_user사건(도착 등), 선호 채널발송 결과문자 또는 TTS 음성전화 — 김순자 씨는 전화규격 검증*
suggest_items이용자, 권수이달의 추천 목록[확장 v0.2] AI 책큐·정보나루 추천 연계구현*
manage_mandate이용자, 동작(생성·조회·해지)구독 위임장[확장 v0.2] 책이지 패스의 동의 장치 — 위임 실행·범위 밖 건너뜀·즉시 해지구현

표의 "상태" 열이 현재 위치입니다. 2026. 8. 28. 기준, 핵심 6종과 자동화 확장 2종 (v0.2 — 구독형 「책이지 패스」용) 여덟 도구 전부가 실제 MCP 전송(stdio JSON-RPC) 위의 참조 서버로 구현되어 적합성 시험 17건을 통과했습니다. 확장 2종이 더하는 것은 동의 방식의 진화입니다 — 건별 확인이 「범위 명시 사전 위임 + 사후 통지 + 즉시 해지」로 바뀌어, 위임 범위 밖(실비 경로)은 시스템이 스스로 건너뜁니다 — 김순자 시나리오 전 단계, 무확인 실행 거부, 실행 후 한도 갱신, 전국 폴백, 그리고 규정 설정 파일 교체만으로 판정이 달라지는 것까지 시험으로 재현되었습니다. 별표(*)는 도서관리시스템 쪽이 모의 커넥터라는 뜻입니다. 모의 커넥터의 함수 다섯 개 목록이 곧 본사업에서 벤더에게 제시할 연동 요구서이며, 실측 소장 데이터(2026. 8. 18. 64건)와 가상 회원 위에서 동작합니다. 실행 계층을 진짜 알파스에 붙이는 일이 본사업의 몫입니다.

04커넥터의 실체 — 번역기 한 편의 속살

커넥터가 실제로 어떤 물건인지, 알파스 커넥터의 check_policy 부분을 의사코드로 보입니다. 읽는 데 프로그래밍 지식이 필요하지 않게 썼습니다 — 줄마다 무슨 일이 벌어지는지가 오른쪽 주석에 있습니다.

alpas_connector / policy.py — 규정 판정의 실제 구현 (의사코드)
RULES = load("config/bucheon.yaml")          # 규정 숫자는 코드가 아니라 설정 파일에 (아래)

def check_policy(user_token, isbn13, pickup):
    member = alpas.member_status(              # 알파스에 회원 현황을 묻는다
        vault.resolve(user_token))             # 진짜 회원번호는 금고 안에서만 풀린다 (5장)

    checks = [
      rule("수령관 동일도서 비치 시 불가",
           not alpas.on_shelf(pickup, isbn13)),          # 상동 서가에 지금 꽂혀 있나?
      rule(f"상호대차 {RULES.ill_limit}권",
           member.ill_count < RULES.ill_limit),            # 김순자 씨는 지금 2권 → 통과
      rule(f"통합 {RULES.total_limit}권",
           member.total_loans < RULES.total_limit),
      rule(f"도서관별 {RULES.per_lib_limit}권",
           member.loans_at(pickup) < RULES.per_lib_limit),
    ]
    return Decision(allowed=all(checks), why=checks)   # 판정 + 근거를 함께 돌려준다

이 파일이 하는 일의 전부가 번역입니다. 왼쪽에서 표준 질문(check_policy)이 들어오면, 알파스가 알아듣는 말(회원 현황 조회, 서가 재고 조회)로 바꿔 묻고, 답을 다시 표준 모양으로 싸서 돌려줍니다. 정보나루 커넥터도, 나중에 만들 다른 시스템 커넥터도 구조가 같습니다.

규정은 코드가 아니라 설정이다

위 코드에 부천의 "5권·20권·5권"이 한 글자도 없다는 점을 봐 주세요. 숫자는 전부 설정 파일에 삽니다. 이 한 수가 6장의 확산을 가능하게 만듭니다.

config/bucheon.yaml — 부천의 모든 지역 고유값
region_code: 31050                # 정보나루 세부지역 코드
libraries: { 상동: 141321, 꿈빛: 141065, … 16개관 }
rules:
  ill_limit: 5                   # 상호대차 1인 한도
  total_limit: 20                # 시 통합 대출 한도
  per_lib_limit: 5               # 도서관별 한도 (직접+상호대차 합산)
  block_if_pickup_on_shelf: true # 수령관 비치 시 신청 불가 규정
sso: sso.bucheon.go.kr
notify_channels: [sms, voice_call]
전일 기준 문제는 여기서 끝납니다. 관내 16개관의 재고·대출은 알파스 커넥터가 실시간으로 답하므로, 정보나루의 D-1 데이터는 "다른 지역에 있나"를 보는 광역 조회와 비상시 폴백으로만 쓰입니다. 시제품의 한계였던 것이 완성형에서는 역할 분담이 됩니다.

05어디서 돌고, 무엇이 지켜지나

물리적 배치는 단출합니다. 공공기관용 클라우드의 가상서버에 에이전트·MCP 서버·정보나루 커넥터·알림 커넥터가 올라가고, 알파스 커넥터만 도서관 정보시스템과 만나는 접점(내부망 연계 구간)을 가집니다. LLM은 API로 호출하며, 계약에 따라 국내 리전·공공 전용 모델로 둘 수 있습니다. 모델 교체가 생겨도 L3 아래는 아무것도 바뀌지 않습니다 — 이것도 MCP 분리의 효과입니다.

개인정보는 어디까지 가는가

가장 예민한 질문이라 표로 못박습니다. 원칙은 하나 — 언어모델은 판단에 필요한 최소한만 보고, 신원은 금고(vault) 밖으로 나가지 않는다.

정보LLM에 전달비고
발화 내용 ("나미야 잡화점…")전달 (익명)누가 말했는지는 안 감. 음성 원본은 기기에서 글자로 바뀐 뒤 폐기
도서명·소장 상태·규정 판정 결과전달답변을 만들 재료
이름·회원번호·연락처전달 안 함임시 토큰(tok_8f3a…)으로 치환. 실번호는 커넥터의 금고에서만 복원
대출 이력 원본전달 안 함"한도 2/5 통과"라는 요약 판정만 전달

그 밖의 안전장치 세 가지. 첫째, 쓰기 도구(request_service)는 confirmed_by_user가 참일 때만 동작합니다 — 확인 없는 실행은 커넥터가 거부합니다. 둘째, 모든 도구 호출은 로그로 남아 "AI가 왜 그렇게 판단했나"를 사후 감사할 수 있습니다. 셋째, 사실(소장·규정)은 전부 도구가 답하므로 LLM이 지어낼 자리가 구조적으로 없습니다 — LLM의 일은 해석과 문장뿐입니다.

06다른 도시가 가져가는 날 — 확산의 실제 절차

이제 핵심 질문. 가령 알파스를 쓰는 A시 도서관이 책이지를 도입하기로 했다면, A시가 실제로 해야 하는 일은 무엇인가? 답: 설정 파일 하나를 쓰고, 이미 있는 부품을 내려받아 조립하는 것입니다. 코딩이 등장하는 순간은 단 한 경우뿐입니다.

#A시가 하는 일성격규모
1도서관 코드표 교체 — 자기 분관들의 정보나루 코드설정반나절
2규정 YAML 작성 — 자기 시의 한도·규칙 숫자설정반나절
3자기 시 SSO 연동 정보 입력설정+협의시 정보부서 협의
4도서관리시스템 커넥터 연결 — 알파스면 부천 것 재사용재사용0 (이미 있음)
5다른 시스템이라면 → 그 시스템용 커넥터 1회 개발개발 (유일)시스템당 1회, 전국이 공유

1~2번이 어떤 일인지는 설정 파일을 나란히 놓으면 바로 보입니다. 왼쪽이 부천, 오른쪽이 가상의 A시 — 다른 것은 숫자와 코드뿐, 시스템은 한 글자도 다시 만들지 않습니다.

1,630여 곳이 각자 앱을 만들면 1,630번의 개발입니다. MCP 구조에서는 도구 서버와 에이전트는 공용이고, 개발은 도서관리시스템 종류 수만큼만 일어나며, 그마저 한 번 만들어지면 전국이 재사용합니다. 이것이 "기관 수가 아니라 시스템 종류 수만큼 개발한다"는 문장의 실제 의미입니다.

08자주 나오는 질문

Q. MCP 서버를 도입하려면 서버(기계)를 새로 사야 하나?
아니요. "서버"라는 말에는 두 가지 뜻이 있습니다 — 서버실의 기계, 그리고 요청을 받아 답을 돌려주는 프로그램(식당의 "서버"가 종업원이듯, 역할 이름입니다). MCP 서버는 후자입니다. 실제로 이 프로젝트의 참조 서버는 파이썬 파일 하나(server.py)이며, 명령어 한 줄로 켜지고 꺼집니다. 컴퓨터 한 대에는 이런 서버 프로그램 여러 개가 동시에 올라갑니다. 예산서에 잡히는 것은 "서버 구입비"가 아니라 시 정보자원 또는 공공 클라우드의 이용료입니다.
Q. 알파스(벤더)가 연동에 협조하지 않으면?
조회까지는 정보나루만으로 시작할 수 있으므로 서비스 개시 자체는 막히지 않습니다. 실행(신청)만 벤더 API가 필요한데, 커넥터 하나로 자사 시스템을 쓰는 전국 도서관이 잠재 고객이 되는 구조라 벤더에게도 사업 기회입니다. 협의가 길어지면 과도기엔 화면 자동화로 대체하는 우회로도 있습니다(권장하지는 않음).
Q. AI가 개인정보를 학습하거나 유출하지 않나?
5장의 표가 답입니다. 이름·회원번호·연락처·이력 원본은 LLM에 아예 전달되지 않고, 임시 토큰과 요약 판정만 오갑니다. 호출 로그가 남아 감사도 가능합니다.
Q. AI가 잘못 알아들으면?
해석 결과는 항상 화면에 근거(서지·ISBN)와 함께 표시되어 이용자가 정정할 수 있고, 실행은 확인 한 번을 거쳐야만 일어납니다. 그리고 소장·규정 같은 사실은 LLM이 아니라 도구가 답하므로, 잘못 알아들어도 "없는 사실"이 만들어지지는 않습니다.
Q. 정보나루 데이터가 전일 기준이라던데?
완성형에서는 관내 실시간을 알파스 커넥터가 맡고, 정보나루는 광역 조회와 폴백만 담당합니다(4장). 시제품 단계의 한계가 완성형의 역할 분담으로 바뀝니다.
Q. 그냥 도서관마다 챗봇 하나씩 만들면 안 되나?
됩니다 — 1,630번 만든다면. 그리고 그 1,630개는 서로 아무것도 공유하지 못합니다. MCP 구조의 요점은 잘 만드는 것이 아니라 한 번 만든 것이 남의 출발점이 되게 하는 것입니다. 상호대차가 장서를 공유하는 제도이듯, 이 설계는 개발을 공유하는 제도입니다.

이 문서는 내부 검토용 시안입니다. 도구 6종 명세는 문체부 공모 원고의 <표 2>와 동일 체계이며, 0단계 산출물(시제품·실측·원고)은 프로젝트 문서고에 있습니다. 알파스 연동 범위·비용은 벤더 견적으로 확정해야 하며, 본 문서의 A시는 설명을 위한 가상 사례입니다.
