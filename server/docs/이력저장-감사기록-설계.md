# 신청·위임 이력의 영속 저장과 감사 기록: 설계와 시험 구현

작성 2026. 9. 27. · 실험실 이용 신청서의 「이용기간 중점 과제」 중 두 가지(이력 영속 저장 계층, 대행 실행의 감사 기록 설계)

## 1. 왜 필요한가

- v0.3까지 위임장(책이지 패스)·신청·한도 현황은 서버 메모리에만 있었다 → 서버를 끄면 동의 기록과 접수 이력이 사라진다. 대행(사람 대신 실행)은 "언제, 무슨 근거로, 무엇을 했나"를 나중에 보여 줄 수 있어야 한다.
- 실험실 이용가이드·서약서가 요구하는 것과도 맞닿는다: 영향이 큰 동작은 사람이 확인하고, 실행 이력을 남긴다.

## 2. 시험 구현(v0.3.1): 무엇을 했나

| 구성 | 파일 | 켜는 방법 | 하는 일 |
|---|---|---|---|
| 영속 저장 | `store.py` | `CHAEKIJI_STORE=경로.sqlite3` | 위임장·위임 일련번호·신청·회원 현황(모의)을 SQLite(표준 라이브러리)에 저장. 상태가 바뀌는 도구(신청·취소·위임 생성·해지·상태 전이)마다 저장, 서버 시작 시 복원 |
| 감사 기록 | `audit.py` | `CHAEKIJI_AUDIT=경로.jsonl` | 모든 `tools/call`을 한 줄씩 덧붙여 기록. 각 줄이 앞 줄의 해시를 품는 **해시 사슬** → 중간 수정·삭제 감지(`python3 audit.py 파일`) |
| 점검 시험 | `lab/check_store.py` | - | 재시작 복원, 취소·해지 보존, 사슬 검증·변조 감지, 최소 기록, 관내 출처 전환(14건) |

환경변수가 없으면 v0.3과 똑같이 동작한다(적합성 시험 33건 그대로 통과).

### 감사 기록 한 줄에 담는 것 / 담지 않는 것

| 담는 것 | 담지 않는 것 |
|---|---|
| 시각, 순번, 도구 이름 | 회원 식별자(m-…) |
| 이용자 토큰의 해시 앞 12자 | 토큰 원문 |
| ISBN, 신청번호, 위임번호 | 발화 원문(길이만) |
| 결과(ok / denied / error), 실패한 규정 이름 | 알림 문구 |
| 실행 근거(이용자 즉시 확인 / 사전 위임 mnd-…) | 인증키 |

```

 "prev":"…앞 줄 해시…","hash":"…"}
```

## 3. 운영 전환 설계(구현하지 않은 것, 예산·구축 단계)

| 항목 | 설계 | 비고 |
|---|---|---|
| 저장소 | 기관 표준 DB(예: PostgreSQL·MariaDB). 표: `mandate`(위임), `mandate_event`(동의·해지·일시정지), `request`(신청), `request_event`(상태 전이), `audit_log` | 시험 구현의 SQLite 표 4개가 뼈대 |
| 원본과 사본 | **신청 상태의 원본은 도서관리시스템**. 책이지 저장소는 "우리가 무엇을 요청했고 무슨 답을 받았나"의 사본 + 위임장의 원본 | 불일치 시 도서관리시스템 우선 |
| 암호화 | 저장 시 암호화(DB TDE 또는 컬럼 암호화), 전송 TLS. 토큰·회원 매핑은 별도 금고(`vault.py`의 운영판)에만 | 【확인】 기관 암호화 기준 |
| 보존·파기 | 위임장: 해지 후 【확인】년 · 신청 이력: 【확인】년 · 감사 기록: 【확인】년(기관 기록물 기준) | 개인정보 처리방침에 명시 |
| 접근 통제 | 사서 역할별 조회 권한, 이용자는 본인 것만(track_request 규칙 그대로) | 감사 기록은 읽기 전용 |
| 감사 시스템 연계 | 해시 사슬 JSONL → 기관 감사 로그 수집기(syslog/SIEM)로 전송, 서명 키는 HSM 또는 KMS | 【확인】 기관 보안 담당 |
| 동시성·가용성 | 행 단위 트랜잭션, 도서관리시스템 야간 배치 시간대 대기열 | v0.3 README 「다루지 않는 것」 항목 |
